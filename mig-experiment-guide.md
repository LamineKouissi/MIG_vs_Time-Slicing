# MIG vs Time-Slice Experiment: The Step-by-Step Educational Guide

This guide is for those who want to understand exactly what happens under the hood during the experiment, rather than simply executing the automated `scripts/run_experiment.sh` script. Below, we break down each step, command, and configuration parameter used in the experiment.

---

## Step 0 — Verify GPU Support for MIG

Before starting, we need to ensure the GPU supports MIG and check its current state.

```bash
# Checks the current MIG mode of the GPU (Enabled/Disabled).
# The --query-gpu flag lets us retrieve specific data fields without parsing the full output.
nvidia-smi --query-gpu=mig.mode.current --format=csv

# Lists the available MIG profiles supported by the physical GPU.
# MIG profiles define how a physical GPU can be sliced (e.g., memory size, compute units).
nvidia-smi mig -lgip
```

## Step 1 — Install Prerequisites

Here we prepare the environment by installing necessary system packages, Python libraries, and the LLM itself.

```bash
# We install required utilities:
# - jq: For parsing JSON output from the benchmarking tool.
# - bc: For performing command-line math operations if needed.
# - curl: To test HTTP endpoints (health checks).
# - python3-venv: To isolate our Python environment.
sudo apt update && sudo apt install -y jq bc curl python3-pip python3-venv

# Set up our working directory
mkdir -p ~/mig-experiment/results
cd ~/mig-experiment

# Isolate dependencies in a virtual environment to avoid system package conflicts
python3 -m venv .venv
source .venv/bin/activate

# Install vLLM, the high-throughput inference engine we will use for benchmarking
pip install vllm

# Verify that Docker is installed and the NVIDIA container runtime is properly configured.
# The NVIDIA runtime allows Docker containers to directly access physical GPUs.
sudo docker info | grep -i runtime
```

### We Pre-Download the Model

```bash
# Downloading the model ahead of time ensures our benchmarking phase isn't delayed
# by network speeds. This script uses the huggingface_hub library to fetch the 7B parameter model.
python3 -c "from huggingface_hub import snapshot_download; snapshot_download('Qwen/Qwen2.5-7B-Instruct')"
```

## Step 2 — Create the Benchmark Scripts

To automate the load generation and results processing, we use a set of small bash scripts.

### 2a. Load Generator — `run_bench.sh`

This script fires a specific number of requests at a specific rate against one of our vLLM instances.

**Command Breakdown:**
- `--backend openai`: We use the standard OpenAI API format supported by vLLM.
- `--model "Qwen/..."`: Specifies the model to run the benchmark against.
- `--random-input-len / output-len`: Keeps our requests standardized by generating 128 tokens in and 128 tokens out.
- `--num-prompts` and `--request-rate`: Controls the total load and the speed at which requests are sent.

*(See the `scripts/run_bench.sh` file for the exact code).*

### 2b. Test Orchestrator — `run_test_pattern.sh`

This script simulates a real-world "noisy neighbor" scenario to test isolation.

**What it does:**
1. Starts a **steady load** on Instance B (port 8001) at a slow 2 requests/second.
2. Waits 30 seconds for this load to stabilize.
3. Fires a massive **spike** of 500 requests at 50 requests/second at Instance A (port 8000).
4. Monitors if the spike on Instance A degrades the latency of the steady load on Instance B.

*(See the `scripts/run_test_pattern.sh` file for the exact code).*

### 2c. Results Comparison — `compare_results.sh`

Extracts data from the JSON files generated by `vLLM bench serve`. 

**What it extracts using `jq`:**
- **TTFT (Time To First Token)**: How long it takes to start receiving an answer (crucial for perceived latency).
- **TPOT (Time Per Output Token)**: The generation speed of the text.
- **TPOT StdDev**: The standard deviation of the generation speed (a measure of stability/jitter).

*(See the `scripts/compare_results.sh` file for the exact code).*

### 2d. GPU Utilization Logger — `gpu_util_logger.sh`

This script loops in the background and queries `nvidia-smi` every second to write GPU utilization and memory usage to a CSV file.

*(See the `scripts/gpu_util_logger.sh` file for the exact code).*

## Step 3 — Phase 1: Baseline (No MIG, Time-Sliced)

In this phase, we launch two containers on the exact same physical GPU. NVIDIA's time-slicing scheduler will rapidly switch between them.

### 3a. We Launch 2 vLLM Instances Sharing the Full GPU

**Command Breakdown:**
- `--gpus all`: Gives the container access to the whole GPU.
- `--ipc=host`: Allows shared memory across the host, required by vLLM for optimized tensor parallel operations.
- `--gpu-memory-utilization 0.45`: **CRITICAL**. Because both instances are sharing the same GPU memory space, we must restrict each instance to 45% of the total VRAM. If we set this to >50%, the second container will crash with Out Of Memory (OOM) errors.

```bash
# Instance A — Port 8000
sudo docker run -d --name vllm-a --gpus all \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8000:8000 --ipc=host \
    vllm/vllm-openai:latest \
    --model Qwen/Qwen2.5-7B-Instruct \
    --gpu-memory-utilization 0.45 \
    --max-model-len 4096

# Instance B — Port 8001
sudo docker run -d --name vllm-b --gpus all \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8001:8000 --ipc=host \
    vllm/vllm-openai:latest \
    --model Qwen/Qwen2.5-7B-Instruct \
    --gpu-memory-utilization 0.45 \
    --max-model-len 4096
```

**Health checks:**
We use `curl` to query the `/v1/models` endpoint to ensure the API server is up before firing traffic.

### 3b. We Run the Baseline Test
Here we run the orchestration script. Because there is no hardware isolation, the spike on Instance A should severely disrupt the latencies on Instance B.

### 3c. We Save and Clean Up
We stop and remove the containers to prepare for Phase 2.

---

## Step 4 — Phase 2: MIG (Hardware Isolation)

Now we carve the physical GPU into distinct hardware partitions using MIG. Each slice has its own dedicated SMs (Compute) and memory bandwidth, completely isolating the workloads.

### 4a. We Enable MIG Mode

```bash
# Tells the driver to put the GPU into MIG mode. This requires a GPU reset.
sudo nvidia-smi -mig 1
```

### 4b. We Create 2× `3g.40gb` GPU Instances

MIG profiles use the format `<Compute_Slices>g.<Memory_Size>gb`. Here we are asking for 3 compute slices and roughly 40GB of memory per instance.

```bash
# -cgi: Create GPU Instance
# -C: Automatically create the corresponding Compute Instances inside them.
sudo nvidia-smi mig -cgi 3g.40gb,3g.40gb -C
```

### 4c. We Launch 2 MIG-Isolated vLLM Instances

To assign a specific MIG slice to a container, we pass the unique UUID of the MIG device to Docker. 

**Command Breakdown:**
- `--gpus '"device=MIG-UUID..."'`: Explicitly binds only this MIG partition to the container. The container thinks it has a full, independent GPU.
- `--gpu-memory-utilization 0.90`: Because the MIG slice is isolated, we don't have to share memory with the other container anymore! We can safely use 90% of the partition's available memory.

```bash
# Instance A — MIG slice 0
# The device string would look something like MIG-11111111-1111-1111-1111-111111111111
sudo docker run -d --name vllm-mig-a \
    --gpus '"device=MIG-UUID"' \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8000:8000 --ipc=host \
    vllm/vllm-openai:latest \
    --model Qwen/Qwen2.5-7B-Instruct \
    --gpu-memory-utilization 0.90 \
    --max-model-len 4096
```

### 4d. We Run the MIG Test

We run the exact same `run_test_pattern.sh` script. Because of hardware isolation, the spike on Instance A should **not** impact the TTFT or TPOT stability of Instance B.

### 4e. We Clean Up Containers

We remove the isolated Docker containers.

---

## Step 5 — Results Comparison

By running `compare_results.sh`, you should observe the following key differences:
- **Baseline (Time-Sliced):** The p99 TTFT on Instance B will degrade severely during Instance A's spike. Time Per Output Token (TPOT) standard deviation will be high, indicating stuttering output.
- **MIG (Hardware Isolation):** The p99 TTFT and TPOT on Instance B will remain completely flat, proving that hardware isolation prevents noisy neighbor interference.

## Step 6 — Teardown

Finally, we destroy the MIG partitions and turn off MIG mode to return the GPU to its normal state.

```bash
# -dci: Destroy Compute Instances
sudo nvidia-smi mig -dci
# -dgi: Destroy GPU Instances
sudo nvidia-smi mig -dgi
# Disable MIG mode
sudo nvidia-smi -mig 0
```
